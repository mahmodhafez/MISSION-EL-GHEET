# Python climate interface • Sakha release v1

`ClimateStore(data_dir: str | pathlib.Path, site_id: str = "sakha_31.10_30.95")` is the integration boundary. `data_dir` contains the complete local weather series, quality flags, fit targets, release and source manifests. All dates in this interface are real `YYYY-MM-DD` strings in local solar time (LST), with no hours, timezone conversions or UTC offsets. The named site is the only supported point (31.10°N, 30.95°E). Return type for every method is a JSON-serializable Python dictionary. Read the machine-generated `example_response.json` for a full input and output; its top-level `request` is an example envelope, not an HTTP endpoint.
 
| Method on the store | Required input and output |
|---|---|
| `get_daily_weather(start: str, end: str)` | Inclusive start/end. Returns `status,start,end,coverage,quality,provenance,units,rows`. Each dated row contains its source snapshot, eight original variables, three ET₀ pathways, flags, statistical columns and disposition. |
| `calculate_et0_summary(start: str, end: str)` | Inclusive interval. Same metadata plus `metrics`: integer `days`, `et0_total_mm` (sum), `mean_et0_mm_day` (sum/days), `tmax_min_c,tmax_mean_c,tmax_max_c` (extrema and arithmetic daily mean). Null metrics unless complete. |
| `calculate_heat_exposure(start: str, end: str)` | Inclusive interval. Returns `definition,hot_days,hot_day_fraction` and range metadata. An observed daily Tmax ≥39.48°C reaches the fixed threshold; equality counts. Count/valid days is a fraction [0,1]. Incomplete intervals return null indicators. |
| `get_climatology(target_date: str, reference: str = "historical_2001_2025")` | Target date selects a calendar slot, so dates outside the observed years are allowed. `quantiles` carries the target date, reference bounds, method, support count and per-variable `q10,q50,q90`. Also returns units, reference_id, coverage and QC of the actual reference sample. This is a historical distribution, not observed weather on the requested date. |
| `get_historical_replay(plan: dict, anchor_years: list[int], *, template_anchor_year: int)` | One dated plan; returns the comparison schema below with one candidate and no paired differences. |
| `compare_historical_plans(plans: list[dict], anchor_years: list[int], *, template_anchor_year: int)` | Ordered candidates; the first is the comparison baseline. Histories use identical eligible anchors, exclusions and the same common envelope. Returns paired candidate-minus-baseline differences. |
| `get_data_provenance()` | `source_receipts` contains summaries of both source captures (raw/derived hashes, request, header, units, time and point). Also returns site and version metadata, date coverage, QC counts, `heat_definition` and scope. The exact original receipt bytes are `sources/power_provenance*.json`. No caller parameters. |

**Sources and indicators.** `provenance` carries `site_id,dataset_version,et0_method_version,time_standard,source_sha256`. Hashes identify the snapshots contributing weather rows to the result. For an empty interval or blocked replay this map is empty. The heat definition is computed once from **all 6,574 fit-period daily Tmax observations (2001–2018)** using linear P90; it is an annual pooled reference, not month- or crop-specific. Use the full provenance call for its underlying historical receipt. The two climatologies pool month/day ±15 across a circular leap calendar: the app default includes only complete years **2001–2025** at source precision; `ml_fit_2001_2018` is the strict train-only float32 benchmark. Neither incorporates the partial 2026 into its reference.

**Coverage and quality.** Interval `coverage` has integer `expected_days,valid_days` and real `fraction` from 0 to 1. Date range queries return `complete,partial,unavailable`; partial weather returns available rows, but partial ET₀/heat totals and fractions are null. `quality.review_days` counts days whose stored disposition is `retain_review`; `flag_day_counts` and `statistical_column_day_counts` count individual flags, may overlap and omit zero-count keys. Header-level product-mix flags describe the whole recent response, not a day-specific instrument; they can occur even if the other flags give `retain`. The release has zero hard-invalid days. See the shared dictionary for units and flag meanings. A zero hot-day count in a complete interval is valid, unlike a missing indicator.

## Plan inputs

| Object | Schema and semantics |
|---|---|
| Plan | Required nonempty text `plan_id,plan_version,field_id,planner_status`, and ordered nonempty list `seasons`. Supply `mapping_policy="explicit_calendar_windows_v1"` for supported replay. Status is supplied by the planner: `feasible,rejected,needs_review`; it never becomes a climate verdict. Optional list `commitments`, default empty. Unknown fields are rejected. |
| Season | `season_id,crop_id,purpose` (nonempty strings), `sow_date,crop_end_exclusive` (dates). Measures crop occupancy **[sow, crop end)**; if a planner means last day in crop, it must convert explicitly using its own contract. Crop end is not a field-release or next-sow date. Supply null explicitly for an unknown endpoint to get a blocked response; omitting the required key is malformed input. |
| Commitment | `id,description,date` (nonempty strings and ISO date). Dates map under the same calendar offsets. The interface does not test whether a mapped crop actually meets that obligation. Candidates must represent the same protected commitment IDs and dates; changing one blocks the paired comparison. |
| Anchors | `template_anchor_year` is the year of each plan's first sowing. Each distinct integer in nonempty `anchor_years` is one replacement year; order of results is ascending. Valid year integers: 1…9999, excluding booleans. The example uses a 2026 template with historical anchors. |

Each candidate must refer to the same field and ordered season slots. Four consecutive planner-supplied seasons are supported; the general interface also accepts shorter sequences. Gaps between supplied crops are recorded as outside-crop days; the module does not invent intervening crops. All explicit endpoints and protected dates shift by the same whole-year offset, retaining month/day. A mapped Feb 29 endpoint or commitment in a non-leap year excludes the anchor for **all** candidates (`unrepresentable_explicit_date`). A Feb 29 inside a window counts as a real extra day. No independent season resampling or sliding of individual dates.

Eligibility is conservative: require complete data from January 1 of the earliest year through December 31 of the latest year touched by any included crop day or explicit commitment. The *measurements* use only the specified crop windows. The common accounting envelope is earliest sow through latest exclusive crop end across the compared plans. Extreme historical years and flagged valid days are kept. A missing calendar year or incomplete 2026 excludes the entire shared anchor; `incomplete_continuous_block` includes expected/observed counts. This whole-year gate can exclude a short window whose own days are present.

## Replay responses and presentation

- Top level: `status,mapping_policy,mapped_feasibility,template_anchor_year,baseline_id,requested_anchors,eligible_anchors,exclusions,blocks,block_variability,paired_difference_variability,blockers,heat_definition,coverage,quality,provenance`. `mapped_feasibility` is always `not_evaluated`.
- `blocks[]`: anchor, calendar-year block ID and inclusive first/last dates, common measurement envelope with exclusive stop, coverage, QC, provenance, profiles for all candidates, and `differences_from_baseline[plan_id]`. `plans[]` carries supplied identifiers/status, mapped commitments, each season's actual bounds/metrics/quality, aggregate `in_crop`/quality, `outside_crop_intervals`, and outside-crop totals (days and mm).
- Every in-crop or gap metric has `days,et0_total_mm,mean_et0_mm_day,tmax_min_c,tmax_mean_c,tmax_max_c,hot_days,hot_day_fraction`. Compare cumulative ET₀ **alongside duration and daily mean**, and hot days alongside hot-day fraction. Gap days have no implied agricultural status, cost or water allocation.
- Variability by plan/block uses count, minimum, median and maximum for duration, total/mean ET₀, mean Tmax, hot count and hot fraction. Paired variability uses the same anchors and additionally counts positive, negative and zero differences. No significance, yield, crop stress, probability of success or optimality is inferred. Overlapping anchors are not independent replicates.
- Status: `complete` all anchors used; `partial` at least one shared block but some excluded; `unavailable` none eligible (no block metrics); `blocked_policy` unsupported mapping, missing actual endpoint, overlapping/unordered windows, or different protected commitments. Do not display a blocked or unavailable result as zero exposure. Surface the affected plan/season and reason.
- `ClimateInputError` is a subclass of `ValueError`: invalid site or calendar dates, reversed/empty intervals, invalid types/fields/IDs, duplicate anchors or structurally incomparable candidates. A one-day inclusive weather interval is valid. `ClimateDataError` is a distinct `ValueError` for missing/corrupt/unsupported release at startup. Responses with no blocks are successful descriptions of data/policy limitations, not equivalent to transport or authentication errors.

## Moving to a later snapshot

Acquire new dated source bytes and receipts in a **new release directory**. Preserve the old release and archives; record capture time, raw hashes, variable units, site and header separately. Validate duplicates, complete dates, permissions to use the data, fill, physical constraints and recalculated ET₀, and quantify overlap/revisions. Add version-specific configuration and regression evidence in the full project; the delivered build and loader intentionally pin this snapshot. Freeze the evaluated development thresholds and historical benchmark; any refit is a new method/version. Have the planner/backend owners exercise this contract in staging with explicit endpoint/commitment semantics and their timeouts. Switch the configured data path/module version together only after those checks; rollback uses the previous immutable copy. No update or forecast is performed by a farmer-facing request.
